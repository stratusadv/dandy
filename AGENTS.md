# AGENTS.md

Guidance for working in the **Dandy** repository (v3.0.0) — a Python AI framework for building LLM-powered software (bots, prompts, structured intel, recording, caching, decoding).

> This document is the **single source of truth** for agent rules in this repo. The previous `.github/copilot-instructions.md` was removed on 2026-09-06; all of its still-accurate content has been absorbed and updated here. When the two disagree, this file wins.
>
> **v3.0.0 was a physical DDD restructure**: every module moved into the five-layer layout described in [DDD layering](#ddd-layering). All import paths in this document reflect the new layout; the old top-level packages (`dandy/llm/`, `dandy/core/`, `dandy/bot/`, `dandy/intel/`, `dandy/tool/`, `dandy/conf/`, `dandy/cli/`, `dandy/http/`, `dandy/file/`, `dandy/cache/`, `dandy/recorder/`) no longer exist.

## Quick orientation

- **Runtime**: Python >= 3.11 (classifiers cover 3.11–3.14); `.python-version` pins 3.11 for local tooling. No `.venv` is committed — create one with `just venv` (uses `uv`).
- **Dependencies** (runtime, deliberate and small): `pydantic`, `requests`, `blessed` (CLI TUI), `python-dotenv`. Dev tooling (the `development` extra): `ruff`, `pytest`/`pytest-cov`, `ty`, `import-linter` (architecture contracts), `build`/`twine`/`setuptools`/`wheel` (packaging), `Faker`, `hypothesis` (property-based compaction tests). `codespell` is not in any extra; CI enforces it via `.github/workflows/codespell.yml` (or run `uvx codespell .` locally).
- **Entry point**: `dandy.interfaces.cli.main:main` exposes the `dandy` console script and the interactive CLI (`dandy/interfaces/cli/`).
- This is a single-package repo (`dandy/` is the library; `tests/` mirrors the layer layout).

- The `live-llm` and `optional-testing` CI jobs need these secrets/env: `AI_API_HOST`, `AI_API_KEY`, `DANDY_SETTINGS_MODULE`, `LLM_AUDIO_MODEL`, `LLM_DEFAULT_MODEL`, `LLM_THINKING_MODEL`, `LLM_VISION_MODEL`, `OPENAI_API_KEY`, `OPENAI_HOST` (with a real `AI_API_KEY`, CI exercises the live-LLM tests that skip in the hermetic job and locally).

## DDD layering

The `dandy/` package is physically organized as a shared kernel plus four layers. The dependency rules are **enforced** by six `import-linter` forbidden-contracts in `pyproject.toml` (`[tool.importlinter]`, run via `just lint-imports` and CI's Architecture Tests step):

| Package | Layer | Role |
|---|---|---|
| `dandy/shared/` | shared kernel | Service/mixin/connector ABCs (`service/`), exceptions, `singleton.py`, typing registry, `utils.py` (`pascal_to_title_case`, `generate_recorder_event_id`, ...), `settings/` (settings singleton, JSON fallback, `get_cli_llm_config`), FS primitives (`files.py`), base64 media detection (`media.py`), subprocess execution primitive (`subprocess.py`), `debug.py`, `constants.py` |
| `dandy/domain/` | domain | Pure value objects & policy: `intel/` (`BaseIntel`, `IntelFactory`, `IntelService`), `tool/` (`BaseTool`, tool-call intel), `prompt/` (Prompt + snippets, LLM-agnostic), `tokens/` (dependency-free token estimation), `message/` (`Message`, `MessageHistory`, `compact_message_history`), `request/` (`LlmOptions`, `LlmRequestBody`, LLM exceptions, pure-string prompt templates), `decision/` (decision intel/exceptions) |
| `dandy/application/` | application | Use cases: `bot/` (`Bot`), `llm/` (`LlmService` + `LlmServiceMixin`), `decision/` (`Decision`, `DecisionService`), `tool/` (`ToolService`), `diligence/` (diligence handlers), `agent/` (the base `Agent` + the CLI's `CodingAgent` child: `agent.py`, `coding_agent.py`, `session_store.py`, `session.py`, `bots/`, `tools/`) |
| `dandy/infrastructure/` | infrastructure | Adapters: `llm/` (`LlmConnector`, `LlmConfig`), `http/` (`HttpConnector`), `file/` (`FileService` + `FileServiceMixin`; the FS primitives they call live in `dandy/shared/files.py`), `cache/`, `recorder/` (the `Recorder` singleton, renderers, and the `*_events.py` event-builder modules), `future/` (thread pool) |
| `dandy/interfaces/` | interfaces | `cli/` — the TUI (`blessed`), `Printer`/`MarkdownRenderer`, and `main.py` |

Rules:

1. **domain** may import only **shared** (never application/infrastructure/interfaces, and never I/O beyond the shared kernel's FS/media helpers).
2. **shared** may import nothing from any layer (it is the bottom of the graph).
3. **application** may import **domain + shared**, and (only at the documented seams) infrastructure; never interfaces.
4. **infrastructure** may import **domain + shared**, and (only at the TYPE_CHECKING-only documented seams) application; never interfaces.
5. **interfaces** may import **application + shared**, and (at the two documented seams) infrastructure.
6. The root `dandy/__init__.py` is the **composition root**: a thin re-export of the public API. It is deliberately outside the contracts — it is the one place allowed to touch every layer.

**Documented seams** (the only cross-layer imports the contracts tolerate; each is an exact `source.module -> imported.module` edge in the relevant contract's `ignore_imports`):

- **application → infrastructure** (the service/mixin composition pattern wiring use cases to adapters): `Bot` → file/http mixins + `bot_events` + futures; `LlmService`/`Decision`/`ToolService` → `LlmConnector`, `LlmConfig`, futures, and the recorder `*_events` builders; diligence classes → `LlmConnector` (TYPE_CHECKING only).
- **infrastructure → application**: TYPE_CHECKING-only annotations (`bot_events` → `Bot`, `decision_events` → `Decision`, `LlmConnector` → `DiligenceHandler`).
- **interfaces → infrastructure**: `printer` → `LlmConfig` (welcome banner shows the resolved CODING model name) plus the `cli` → `coding_agent` entry edge (which reaches the seams transitively).

When you add a genuinely new cross-layer import, add its **exact** module-level edge to the right contract's `ignore_imports` (import-linter matches exact `a.b.c -> x.y.z` pairs — package prefixes do not match) and say in the PR why the seam is justified. Otherwise fix the design: move the symbol to a shared layer or depend through an existing port.

## Environment & settings (least obvious part)

Dandy resolves runtime config through a settings module, not constructor args:

1. Importing `dandy` instantiates a `DandySettings` singleton (`dandy/shared/settings/settings.py`) that imports a user settings module named by `DANDY_SETTINGS_MODULE` env var, defaulting to `dandy_settings` (`dandy/shared/settings/load.py`, `dandy/shared/constants.py`).
2. The settings module must define `BASE_PATH` (project root). Everything else falls back to `dandy/shared/settings/default_settings.py`.
3. `LLM_CONFIGS` is a dict; a `DEFAULT` entry is **required** (`dandy/infrastructure/llm/config.py`). Other configs inherit missing `HOST`/`PORT`/`API_KEY` from `DEFAULT`. LLM errors quote the settings module name, so cite that file when users see "is not set" messages.
4. In this repo `tests/dandy_settings.py` is the settings module (configs: `DEFAULT`, `THINKING`, `AUDIO`, `VISION`). It defaults `AI_API_HOST`/`AI_API_KEY`/`LLM_*_MODEL` to hermetic placeholders so `LlmConfig` validates without a live endpoint; real env vars override them. CI injects `DANDY_SETTINGS_MODULE` (+ `AI_API_*`, `LLM_*_MODEL`) as secrets.
5. The CLI auto-creates a `dandy_settings.py` if missing (`dandy/interfaces/cli/utils.py::check_or_create_settings`, which copies `dandy/shared/settings/default_settings.py`) and loads env from `dandy.env` / `development.env` / `dev.env` / `.env`.
6. **JSON fallback**: when neither the settings module nor a JSON file imports, `DandySettings.load_user_settings` (`dandy/shared/settings/settings.py`) falls back to loading settings from a JSON file before the CLI creates a `.py`: first `Path.cwd() / DANDY_LOCAL_DIRECTORY_NAME / 'dandy.json'` (i.e. `.dandy/dandy.json`), then `Path.home() / '.config' / 'dandy' / 'dandy.json'`. The loader (`dandy/shared/settings/load.py::load_settings_from_json_file`) returns a `SimpleNamespace`: top-level keys are upper-cased (`llm_configs` -> `LLM_CONFIGS`), `LLM_CONFIGS` config-name keys and each config's own keys are upper-cased (but `OPTIONS` sub-keys stay lowercase — they are `LlmOptions` field names), `CLI_CONFIG` keys and values are upper-cased (values reference `LLM_CONFIGS` names), and `BASE_PATH`/`CACHE_SQLITE_DATABASE_PATH` strings become absolute `Path`s. A missing `BASE_PATH` defaults to `Path.cwd()`. `check_or_create_settings` probes the same two JSON locations before writing `dandy_settings.py` and prints `Loaded settings from "<path>"` when one is found. Tests live in `tests/interfaces/cli/test_json_settings.py`.
7. **Token estimation & agent compaction**: token counts come from `dandy/domain/tokens/estimate.py` — a dependency-free character-class heuristic (fitted to BPE tokenizer output; letters ~4.65 chars/token, digits ~2, symbols ~1.5, whitespace near-free) plus per-message/per-content costs: chat-template role overhead, tool-call framing ids/names/arguments, image tokens by `detail` (low = 85, high/auto = 765), and audio base64. `Message.estimated_token_count` (`dandy/domain/message/message.py`) branches per content type on the wire form — it does **not** count pydantic reprs anymore. **Context management comes from `CONTEXT_SIZE` in `LLM_CONFIGS`** (e.g. `'CONTEXT_SIZE': 65536` on `DEFAULT`; non-`DEFAULT` configs inherit it from `DEFAULT`, and it also works through the `dandy.json` fallback). `max_completion_tokens` is a normal option in a config's `OPTIONS` (when omitted, no output cap is sent). Every `Agent` resolves its window once at construction (`Agent._resolve_context_size` reads `bot.llm.config.context_size`, falling back to a 65536 constant) and `Agent.turn` compacts `self.history` via `compact_message_history` (`dandy/domain/message/message.py`) to `max_context_tokens * AGENT_COMPACTION_TARGET_RATIO` (constant `0.70`, defined in `dandy/application/agent/agent.py`) minus the real incoming prompt's token estimate, leaving 30% of the window as headroom for output and per-request overhead (system message + tool schemas measure ~2k tokens): the message in the system slot is always kept, the newest message is kept unless it is a `tool` result (then its whole round — declaration plus results — is dropped, since a tool result without its declaration is invalid on the wire), oldest tool-use rounds drop first then oldest plain exchanges, and progress is reported via the `progress_callback` (`Compacting conversation history (...) tokens...`). `CodingAgent` (the CLI's child of `Agent`) runs its planning pass in the base `_prepare_message` hook before compaction, so the 'Implementation Plan' section is part of the incoming estimate; the planning bot starts from a fresh conversation on every turn. If the history still exceeds the whole window after compaction, `turn` raises `AgentRecoverableError` (the CLI prints it) instead of sending a request the provider will 400. Tool results are capped at 8000 characters before entering the conversation (see the tool-calling bullet). Without any `CONTEXT_SIZE` the config still works and compaction falls back to a 65536 window constant. Tests: `tests/domain/tokens/test_estimate.py`, `tests/infrastructure/llm/config/test_config.py`, `tests/application/agent/test_coding_agent.py`.
8. **`DEBUG` mode**: if `DEBUG = True` in settings, `tests/dandy_settings.py` (and `dandy_settings.py` templates) do `from dandy.shared.debug import *`, which replaces `warnings.showwarning` with a stack-trace-printing handler used to debug LLM retry/validation issues.

## Architecture & data flow

### The mixin/service pattern (used everywhere)

Three layers, consistently named:

- **`BaseServiceMixin`** (`dandy/shared/service/mixin.py`): `_get_service_instance(ServiceClass)` lazily builds and caches a service on `self` (`_{ServiceName}_instance` attr). Mixins expose it via a property (`self.llm`, `self.file`, `self.http`, `self.intel`). `_required_attrs` + `__init_subclass__` raise `ServiceCriticalError` if a required class attr is `None` — define class-level defaults before subclassing.
- **`BaseService`** (`dandy/shared/service/service.py`): generic service wrapping the owner (`self.obj`), carries a `recorder_event_id`, calls `__post_init__` hook. `reset()` is abstract; subclasses implement it (the chain relies on call `super().reset()`).
- **`Bot`** (`dandy/application/bot/bot.py`) composes `FileServiceMixin, LlmServiceMixin, HttpServiceMixin, IntelServiceMixin` (MRO order matters — reset chains up through them). The file/http mixins live in `dandy/infrastructure/` — importing them is one of the documented application → infrastructure seams.

**Reset chain** (verified by `tests/application/bot/test_reset_chain.py`): `Bot.reset()` propagates to `llm`, `http`, `intel`, `file` services. The **decision service is deliberately not reset** (`DecisionService.reset()` is a no-op).

Convention: tests keep their fakes and fixtures under a nested **`intelligence/`** directory beside the tests (e.g. `tests/application/bot/intelligence/`, `tests/domain/decision/intelligence/`). The agent is the exception: it lives in `dandy/application/agent/` (the base `Agent`, the CLI's `CodingAgent`, and the `bots/` and `tools/` inside). Follow the `intelligence/` convention when adding fakes or fixtures.

### Public API surface

`dandy/__init__.py` (the composition root — the only module allowed to import every layer) re-exports the curated API: `Agent`, `Bot`, `Prompt`, `BaseIntel`, `BaseListIntel`, `BaseSkill`, `BaseTool`, `Decision`, `DefaultIntel`, `LlmOptions`, `MessageHistory`, `Recorder`, `MemoryCache`, `SqliteCache`, `cache_to_memory`, `cache_to_sqlite`, `generate_cache_key`, `process_to_future`, `recorder_to_html_file`/`recorder_to_json_file`/`recorder_to_markdown_file`, and exceptions `DandyError` / `DandyCriticalError` / `DandyRecoverableError`. The same API is also exposed as the `Dandy` namespace class defined in that file (`from dandy import Dandy`, then `Dandy.Bot`, `Dandy.Prompt`, ...) — it must stay a pure re-binding (docstring + class attributes, no methods) because the file must remain a thin re-export layer with no logic.

### LLM flow

```
Bot.process(prompt, intel_class=..., include/exclude=..., intel_object=...)
  → LlmService.prompt_to_intel  (dandy/application/llm/service.py)
    → LlmConnector.prompt_to_intel (dandy/infrastructure/llm/connector.py)
        builds LlmRequestBody + JSON schema from IntelType (IntelFactory.intel_to_json_inc_ex_schema)
        always prepends a system message; asserts >= 1 system + 1 user message (LlmCriticalError)
        pre/post-diligence handlers run around the HTTP call
        → HttpConnector.request_to_response (retries HTTP_CONNECTION_RETRY_COUNT + 1 times)
        → IntelFactory.json_str_to_intel_object parses response into Intel
        on pydantic ValidationError → retry (option prompt_retry_count, default 2) re-prompting with validation errors
```

- Message history persists on the connector between calls; `Bot.reset()` / `LlmService.reset()` clears messages and re-applies options from settings.
- `include_fields`/`exclude_fields` trim the generated JSON schema so the model only needs to produce those fields (see Intel below).
- Multimodal: `prompt_to_intel` accepts `audio_urls/file_paths/base64_strings` and `image_urls/file_paths/base64_strings` (see `tests/assets/{audio,images}` and `tests/application/bot/test_bot_vision.py`).
- **`LlmOptions`** (`dandy/domain/request/options.py`, a pydantic model with `extra='allow'`): `frequency_penalty`, `presence_penalty`, `top_p`, `temperature`, `prompt_retry_count` (default `2`). Non-None values are range-checked (e.g. temperature 0–2); violations raise `LlmCriticalError`. `max_completion_tokens` is **not** an option — it is derived from the config's `CONTEXT_SIZE` (see [Environment & settings](#environment--settings-least-obvious-part) bullet 7).
- `LlmConfig` (`dandy/infrastructure/llm/config.py`) hard-codes `url.path_parameters = ['v1','chat','completions']` — providers must be OpenAI-compatible chat completions. Non-`DEFAULT` configs inherit `HOST`/`PORT`/`API_KEY` from `DEFAULT`.

### Prompt building

`Prompt` (`dandy/domain/prompt/prompt.py`) is a dataclass (`input: Self | str | None`, `tag: str | None`) that appends **snippets** (`dandy/domain/prompt/snippet.py`) and joins them in `to_str()`. When `tag` is set, output is wrapped in `<tag>...</tag>`. All builder methods return `self` for chaining:

`text`, `heading`, `sub_heading`, `title`, `list`/`unordered_list`, `ordered_list`, `array`, `array_random_order`, `unordered_random_list`, `dict`, `divider`, `line_break` (alias `lb`), `file`, `directory_list`, `intel`, `intel_schema`, `module_source`, `object_source`, `prompt`, `random_choice`. Most accept `triple_backtick`/label kwargs. `estimated_token_count` uses the character-class heuristic in `dandy/domain/tokens/estimate.py` (see [Environment & settings](#environment--settings-least-obvious-part) bullet 7).

### Tool calling

- **`BaseTool`** (`dandy/domain/tool/tool.py`, exported from `dandy`) is an **abstract** base-level tool descriptor (`ABC`), written **inheritance-style like `Bot`**: subclasses set `name` and `description` as class attributes and **must** override the abstract `handle(self, ...) -> str | BaseIntel` with **typed, annotated** keyword parameters (`BaseTool` cannot be instantiated without an override — the abstract `handle` body raises `NotImplementedError`). The handle signature becomes the tool's OpenAI `function` parameters (`to_function_dict()`, validated at call time — a missing `name` raises `ToolCriticalError`): `BaseTool.get_parameters_intel_class()` derives the parameter schema via `IntelFactory.callable_signature_to_intel_class(self.handle)` (the bound method, so `self` is stripped; it is cached per instance). Required-vs-optional follows the signature (no default = required; pydantic omits the `required` key entirely when nothing is required). A handle with no parameters yields a schema with empty `properties` (a no-argument tool). There are **no** `intel_class` or `include_fields`/`exclude_fields` attributes — parameters always come from the handle signature alone. It is LLM-agnostic (the `dandy/application/tool/` subsystem is one consumer, others are free to use descriptors + `handle()` standalone). `BaseTool` also carries the subprocess helper: a module-level `run_subprocess(command, cwd, timeout_seconds, use_shell=False)` free function (`dandy/shared/subprocess.py`, re-exported from `dandy/domain/tool/tool.py`, 8000-char output cap, never raises) plus an instance method `self.run_subprocess(command, timeout_seconds=None)` that applies the tool's `working_directory` property (defaults to `Path.cwd()`), `timeout_seconds = 30`, and `use_shell = False` class attributes — so subprocess tools just call `self.run_subprocess(...)` and set those attrs/override the property.
- **Premade tools**: tools are reusable because each carries its schema **and optionally its execution**:
  ```python
  class GetWeatherTool(BaseTool):
      name = 'get_weather'
      description = 'Get the current weather for a location.'

      def handle(self, location: str = '', units: str = 'celsius') -> str:
          return weather_service.get(location, units)
  ```
  Every tool is self-contained because `handle()` is mandatory and carries the execution; an external `tool_functions` handler can still take over at call time (see below). `tools=[...]` accepts a mix of classes and instances (`to_tool_instances()` normalizes everything to instances before the wire call).
- **Handle dispatch**: at `ToolService._process_tool_call`, arguments are validated against the derived schema and the validated keyword dict is passed straight through (`tool.handle(**arguments_intel.model_dump())`), so defaults are applied and values are Python-typed (a `bool`/`int`/nested annotation is parsed, not left as JSON text). An external `tool_functions` entry still wins and receives the parsed argument Intel object (its `ToolHandler = Callable[[BaseIntel | str], str | BaseIntel]` contract is unchanged). Empty/whitespace arguments are treated as `{}` so no-argument tools handle `arguments: ""` from providers. Because `handle` is abstract, a tool class without an override cannot even be instantiated (it must always declare the schema); no-argument tools declare `handle(self)` and receive no kwargs. Every CLI tool (`dandy/application/agent/tools/`) follows this pattern.
- **Execute-and-loop**: `bot.llm.tools.prompt_to_intel(prompt, intel_class, tools=[...], tool_functions={'name': handler}, max_tool_iterations=5, progress_callback=...)` (`ToolService`, `dandy/application/tool/service.py`) keeps calling the model, executing any requested tools (an explicit `tool_functions` entry wins over the tool's own `handle()`), feeding results back as `role='tool'` messages, until the model returns the final Intel. The original prompt is only sent on the first iteration (history carries it after that). An optional `progress_callback: Callable[[str], None]` gets one beat per tool round for a running narrative: if the model wrote a narration sentence alongside its tool calls, the connector captures it on the returned `ToolCallsIntel.summary` (`dandy/domain/tool/intel.py`, from the assistant `content`) and that sentence is emitted; and one beat is emitted as each tool actually executes — the tool's optional `action_sentence(**validated_args)` override (`dandy/domain/tool/tool.py`, receiving the validated keyword arguments so it can name the exact files or commands), falling back to the tool name via `pascal_to_title_case` (`dandy/shared/utils.py`, e.g. `'get_weather'` → `'Get Weather'`). A tool returns `None` from `action_sentence` to opt out; the agent's own tools all implement it (e.g. `read_file` → 'Reading src/foo.py lines 1-10', `run_command` → 'Running "pytest -q"'), so the CLI story shows exactly what each tool is doing. The service strips the trailing period from each action beat before it reaches `progress_callback` (`removesuffix('.')`), so story beats read 'Reading src/foo.py lines 1-10' without colliding with the model's narration sentence, which keeps its natural period. The CLI bots are prompted to narrate each step ("Begin every message that calls a tool with one short, natural sentence...") so the CLI can render a story. `max_tool_iterations` caps how many tool rounds run before a final answer (default `5`; exceeding it raises `LlmRecoverableError`). Passing `max_tool_iterations=None` disables the cap so the loop never gives up — the CLI's coding and planning agents opt into this. The loop also **compacts its own accumulated conversation before every round** (`ToolService._compact_history_before_next_round`, using the shared `compact_message_history` in `dandy/domain/message/message.py`): it targets `0.70` of the resolved config's `CONTEXT_SIZE` (falling back to a `65536` window when unset; `LlmService.config` exposes the resolved `LlmConfig`), so an unbounded tool-calling session can never overflow the provider's context window — for the coding agent this compacts the same persistent history its pre-chat compaction trims. **Tool results are capped at 8000 characters** before they enter the conversation: `ToolService` truncates any result (a tool's `handle()` return or an external handler's, string or JSON dump) with a `... (truncated)` marker, and the built-in `read_file` / `list_directory` tools cap their own output the same way (matching the 8000-character caps `search_files` and `run_command` already had) — so one oversized result can never blow past the window or be silently dropped whole by compaction. An optional `verbose_callback: Callable[[str], None]` gets one line per event for debugging: the round number and tool-call count, each tool's arguments and result (truncated previews, newlines escaped), arguments that fail validation (fed back to the model), and a `GAVE UP` line when a finite cap is hit.
- **Handlers** are plain callables `Callable[[BaseIntel | str], str | BaseIntel]` — they receive the **parsed arguments Intel** (validated against the tool's handle-derived schema) and return a string or Intel (dumped to JSON) fed back to the model. An unknown tool name raises `LlmCriticalError`; invalid arguments (pydantic `ValidationError`) are fed back to the model as a tool message so it can self-correct; exhausting a finite `max_tool_iterations` raises `LlmRecoverableError` (when it is `None` the loop never gives up, at the cost of unbounded API spend).
- **Skill tools join the per-round tool array** (see [Skill](#skill-dandyskill)): `ToolService.prompt_to_intel` rebuilds the round's tools from your `tools=[...]` plus `SkillService.active_tools()` every round, so a passive skill that activates mid-loop adds its `{skill}_{method}` tools to the next round and `activate_skill` drops off once every passive skill is active (monotonic growth — provider-safe). The call-time `tools` and skill tool names must not collide; `ToolService._validate_no_tool_name_collision` fails fast with `LlmCriticalError` before any HTTP. The wire `tools` field maps an empty round to `None` (the connector clears `response_format` whenever `tools is not None`), so a bot with neither user tools nor skill tools still gets strict JSON mode.
- **Manual path**: calling `bot.llm.prompt_to_intel(..., tools=[...])` directly returns `ToolCallsIntel` (a `BaseListIntel` of `ToolCallIntel` with `name`/`arguments`/`id`) instead of the requested Intel — inspect it and continue the conversation yourself. Tool classes are accepted here too.
- **Wire**: `tools`/`tool_choice` are explicit fields on `LlmRequestBody`; `Message`/`MessageHistory` support `role='tool'` messages (`add_message(role='tool', tool_call_id=..., text=...)`) and assistant `tool_calls`. `Message.model_dump()` emits the OpenAI wire shape (tool content as string, assistant tool_calls with `content: None`).
- **Gotcha**: when `tools` is passed, `response_format` (strict JSON-schema mode) is **cleared** on the request body — strict response_format + non-strict tools 400-errors on OpenAI. The final answer is still validated locally by Dandy's Intel validation + retry loop.

### Decision

- `DecisionService` (`dandy/application/decision/service.py`) exposes `prompt_to_value` (single, wraps `..._values[...][0]`) and `prompt_to_values`, plus `*_future` variants. Access via `self.llm.decision` (DecisionServiceMixin) — not a standalone component.
- `decision.process()` (`dandy/application/decision/decision.py`) requires **all `keys_values` keys to be strings** (raises `DecisionCriticalError` otherwise — values can be any type). Returns `DecisionValuesIntel` (appendable). Keys are auto-numbered 1..n and the LLM returns which it chose.
- Retry loop: on empty result → `DecisionNoChoicesRecoverableError`, on too many → `DecisionTooManyChoicesRecoverableError`, each re-prompts via `LlmConnector.retry_request_to_intel` until `prompt_retry_count` exhausted, then re-raises.
- `.as_enum()` on a `Decision` builds a runtime `Enum` from the mapping for type-safe handling.

### Agent (`dandy/application/agent/agent.py`)

- `Agent` (exported from `dandy`) is the stateful, loop-ready base class: it wraps a `Bot` and owns a `MessageHistory`. A **turn** (`agent.turn(message)`) is one exchange — compact (same 70%-of-`CONTEXT_SIZE` target as the coding agent), then one tool loop (`max_tool_iterations=None`) over the persistent history; the vocabulary ladder is run > turn > tool round.
- `agent.run(request)` drives turns until completion: the first turn gets the request, later turns get a continuation nudge (`continuation_prompt` in `agent/prompts.py`); a turn is done when its result's `done` field is true (default `AgentTurnIntel` = `text` + `done`) or an `is_done` callback says so; a finite `max_turns` exhausted → `AgentRecoverableError`; no `done` field and no `is_done` → `AgentCriticalError` (fail fast). `clear()` resets history + bot (a subclass's `clear` should call `super().clear()` first). `save_session()` snapshots the history plus metadata (last request, model/config names, token count) into an `AgentSession`, and `load_session(session)` restores it into a fresh `MessageHistory` and resets the bot, so a conversation can outlive the process; `SessionStore` (`dandy/application/agent/session_store.py`) persists those as one JSON file per named session under a directory (`for_project(path)` → `<path>/.dandy/agent/sessions/`), with `save`/`load`/`delete`/`latest`/`list_sessions` and `new_name(text)` for auto-naming (`YYYY-MM-DD-<slug>`, collisions get `-2`/`-3`). Subclasses hook `_prepare_message` to shape the incoming message before each turn. `CodingAgent` (the CLI's interactive agent) is a child of `Agent` whose `_prepare_message` runs the planning bot and folds the plan into the turn's prompt.
- Hermetic tests in `tests/application/agent/test_agent.py` mock `HttpConnector.request_to_response` (reuse `ToolBot`/`WeatherTool` from `tests/application/tool/intelligence/` and `content_response`/`tool_call_response` from `tests/application/agent/intelligence/llm_responses.py`).

### Skill (`dandy/domain/skill/skill.py`)

- **`BaseSkill`** (exported from `dandy`) is a pure descriptor: class attrs `name`, `description`, `prompt`, `active` (default `True`, overridable at instantiation: `WeatherSkill(active=True)`), and `tools: list[str]` (method names). Each declared method is exposed as a tool named `{skill}_{method}`; the docstring first line is the tool description and the typed signature is the parameter schema (same rules as a tool's `handle` — every parameter annotated). `to_skill_instances()` normalizes classes/instances; `get_method()`/`method_description()` are the validation helpers; missing/private/non-callable declared methods raise `SkillCriticalError`.
- **`SkillService`** (`dandy/application/skill/service.py`, via `SkillServiceMixin` on `LlmService` — access `bot.llm.skills`) is the registry: `register(skills)` validates (unique skill names, passive skills need a description, no generated-tool-name collisions, `activate_skill` reserved) and builds `SkillMethodTool` instances; `system_prompt_section()` renders the skills block (active: name + full prompt; passive: name + description + an instruction paragraph pointing at `activate_skill`); `active_tools()` returns the method tools of every active-or-activated skill plus the `ActivateSkillTool` while any passive skill is unactivated; `activate(name)` is the `activate_skill` handler (unknown/already-active → a polite string result; success → marks activated and returns the prompt text so it enters the conversation as a `role='tool'` message); `reset()` clears activation only (one-way per conversation; `bot.reset()`/`Agent.clear()` start fresh).
- **Registration surfaces**: on a `Bot` the class attr `skills: list[SkillType]` (alongside `role`/`task`/`guidelines`; `LlmService.__post_init__` registers it and appends the section to the system prompt); on an `Agent` the constructor arg `skills=[...]` (registered on the shared bot at construction, then `LlmService.append_system_prompt(section)` — that method exists for post-init registration and must be called before the first request). The section is static per conversation and never rewritten mid-loop.
- **Wire behavior**: skill tools join the tool loop's per-round array (see [Tool calling](#tool-calling)); a passive skill's prompt enters the conversation via the `activate_skill` tool result (the Anthropic Agent Skills pattern: metadata in the system prompt, instructions loaded on demand). Colliding user-tool/skill-tool names raise `LlmCriticalError` before any HTTP.
- **Hermetic tests**: `tests/domain/skill/test_skill.py` (descriptor), `tests/application/skill/test_service.py` (registry), `tests/application/skill/test_tool_loop.py` (per-round wire assertions — the connector mutates one shared `request_body`, so these snapshot `request_intel.json_data` with a `deepcopy` in a `side_effect` callable; reading `call_args_list[i]` by index gives the *final* state, not the round's), and `tests/application/agent/test_agent_skills.py` (Agent surface, activation across turns, `clear()` re-exposing `activate_skill`). Skill fakes live in `tests/application/skill/intelligence/skills.py`.

### Intel (`dandy/domain/intel/intel.py`)

- `BaseIntel(BaseModel, ABC)`. Everything an LLM returns is an Intel (pydantic) model.
- `model_inc_ex_class_copy(include=..., exclude=...)` builds a **runtime auto-generated subclass** (via pydantic `create_model`) with only the listed fields; use nested dicts `{field: {...}}` for deep filtering of nested Intel. Include and exclude together → `IntelCriticalError`; unknown field names also raise. `model_to_kwargs()`, `model_json_inc_ex_schema`, `create_from_file`/`save_to_file`, `model_validate_and_copy`/`model_validate_json_and_copy` are the other helpers.
- `IntelFactory` (`dandy/domain/intel/factory.py`) maps Python types ↔ JSON schema and validates LLM responses; `IntelService` (`dandy/domain/intel/service.py`) exposes static wrappers: `intel_class_from_callable_signature`, `intel_class_from_simple_json_schema`, `json_str_to_intel_object`.

### Recorder

- `Recorder` is a `Singleton` (`dandy/shared/singleton.py`). `Recorder.start_recording(name)` … `stop_recording(name)`, then `to_html_file` / `to_json_file` / `to_markdown_file` (renderers under `dandy/infrastructure/recorder/renderer/`, HTML templates under `html_templates/`). Recordings write to `{BASE_PATH}/{DANDY_LOCAL_DIRECTORY_NAME}/recordings/`; requires `ALLOW_RECORDING_TO_FILE = True`.
- `Bot.__init_subclass__` installs a **custom `__getattribute__`** that lazily wraps `process` with `record_process_wrapper` (`dandy/infrastructure/recorder/bot_events.py`), so every `process()` call auto-record events. The other per-subsystem event builders live beside it in the same adapter: `llm_events.py`, `tool_events.py`, `decision_events.py`, `diligence_events.py`. See Gotchas about not overriding it.

### Caching

- `MemoryCache` / `SqliteCache` (pydantic `BaseCache` subclasses, `cache_name`/`limit`) + decorators `cache_to_memory` / `cache_to_sqlite` and `generate_cache_key` hashing (`dandy/infrastructure/cache/`). `CACHE_KEY_HASH_LAYER_LIMIT = 3` in `dandy/shared/constants.py` intentionally caps how deep cache keys hash (higher pulls in unwanted attrs).

### Futures

- `dandy/infrastructure/future`: `AsyncFuture` runs callables on a module-level `ThreadPoolExecutor` (max workers = `FUTURES_MAX_WORKERS`). `Bot.process_to_future`, `LlmService.prompt_to_intel_future`. Timeout → `FutureRecoverableError`; non-positive timeout → `FutureCriticalError`.

## Conventions & style

- **Ruff** (`ruff.toml`): single quotes (format-enforced), indent-width 4, line-length **100**, target py311, `select = ["ALL"]` with an explicit ignore list (includes docstring rules D1xx, `ANN001/002/003/401`, `PLR0913/0915`, `SLF001`, `T201`, etc.). New code must pass `ruff check .` **and** `ruff format .`.
- **Naming**: Classes PascalCase, functions/methods snake_case, constants UPPER_SNAKE_CASE, modules/dirs snake_case. Verbose names preferred (`include_fields` not `include`), no single-letter names.
- **Imports**: stdlib → third-party → `dandy.*`, absolute paths only (note `ruff.toml` `known-first-party = ["system", "app"]` — isort otherwise treats `dandy` as first-party automatically). **Inside the framework (`dandy/` and tests), never import from the `dandy` package root** (`from dandy import X`): the root `__init__` eagerly imports every layer, so a root import from within a framework module hits a partially-initialized `dandy` and is the #1 circular-import trap. Always import the defining module's full path instead — `from dandy.application.bot.bot import Bot`, `from dandy.domain.prompt.prompt import Prompt`, `from dandy.infrastructure.recorder.recorder import Recorder`, `from dandy.domain.tool.tool import BaseTool` — which pulls in only that module's dependency subtree. The one sanctioned in-package shortcut is `dandy/shared/settings/settings.py`'s function-level `from dandy.shared.settings import default_settings  # noqa: PLC0415` (deliberately lazy to break the settings load cycle; keep it). **Framework consumers / user code** import the core API from the root (`from dandy import Bot, Prompt, BaseIntel, BaseTool, Recorder, MemoryCache, ...`) — that's exactly what `dandy/__init__.py` re-exports, and that file must stay a thin re-export layer with no logic.
- **Layer discipline**: respect the [DDD layering](#ddd-layering) rules. New imports across layers fail `just lint-imports` (and CI) until either the design is fixed or the exact edge is added to the relevant contract's `ignore_imports`.
- **Type hints**: always annotate signatures; `X | Y` union syntax (Python 3.11+). Generic class names are typed in-string (e.g. `BaseService['dandy.application.llm.mixin.LlmServiceMixin']`) because of deferred annotations.
- **Exceptions**: `DandyError` (base) → `DandyCriticalError` (fail fast / programming error) and `DandyRecoverableError` (retry or fallback) in `dandy/shared/exceptions.py`; each subsystem extends these in its own `<module>/exceptions.py` (e.g. `DecisionNoChoicesRecoverableError`, `DecisionTooManyChoicesRecoverableError`, `IntelCriticalError`, `LlmRecoverableError`, `LlmCriticalError`, `HttpConnectorRecoverableError`, `FutureCriticalError`, `ServiceCriticalError`, `RecorderCriticalError`).
- **No comments in code unless asked**; when present, comments explain *why* (see the LLM-freeze warning in `tests/application/bot/test_bot.py`).

## Testing approach

- `unittest.TestCase` classes, discoverable by both `pytest` (just) and `unittest` (CI: `python -m unittest discover -v -t . ./tests`). The `-t .` flag matters: it makes discovery import `tests` as a package so `tests/__init__.py` (which sets the `DANDY_SETTINGS_MODULE` default) runs; without it, test modules import as top-level and the settings default is never set. No pytest fixtures or conftest — anything pytest-only breaks the unittest runner. Mocking is via `unittest.mock` (`mock.patch(...)`).
- **Test intelligence lives beside the tests** under `tests/<layer>/<module>/intelligence/` (e.g. `tests/application/bot/intelligence/bots.py`, `intel.py`).
- **Live-LLM tests are skipped by default** via `@live_llm_test` (`tests/consts.py`): they run only when `AI_API_KEY` is set and is **not** one of the placeholder values in `_PLACEHOLDER_API_KEYS` (`test-key`, `changeme`, `your-api-key`, `placeholder`). `@run_llm_configs()` (`tests/shared/decorators.py`) does the same at runtime via `self.skipTest(...)` and only loops over `TESTING_LLM_CONFIGS` (`tests/consts.py`, currently `['DEFAULT']`). `tests/dandy_settings.py` supplies placeholder config values so hermetic tests can build `LlmConfig`s. For hermetic LLM tests, patch at the connector boundary: `mock.patch('dandy.infrastructure.http.connector.HttpConnector.request_to_response', ...)` returning `HttpResponseIntel(status_code=200, json_data={'choices': [{'message': {'content': '<json>'}}]})`.
- **Tool calling is tested hermetically**: `tests/domain/tool/test_tool.py` covers the abstract base (cannot instantiate without `handle`, the abstract `handle` raising `NotImplementedError`), schema generation from handle signatures (defaults, required params, no-parameter tools, missing-name `ToolCriticalError`, derived-class caching, `to_tool_instances` normalization); `tests/application/tool/test_service.py` mocks `HttpConnector.request_to_response` with a `side_effect` list of `HttpResponseIntel`s — first a `tool_calls` message, then the final-content message — and asserts on the request bodies (`request_intel.json_data['messages']`, `['tools']`, absence of `response_format`) to verify the loop/history/wire behavior, plus the `handle()` dispatch path. Tool fakes live in `tests/application/tool/intelligence/`.
- **Skills are tested hermetically**: `tests/domain/skill/test_skill.py`, `tests/application/skill/test_service.py`, `tests/application/skill/test_tool_loop.py` (per-round tool-array snapshots via a `deepcopy` `side_effect` — see the Skill section), and `tests/application/agent/test_agent_skills.py`.
- **The CLI is an agentic loop with no action system**: `dandy/interfaces/cli/cli.py` (`DandyCli`) is a pure agent REPL — every message typed goes to `CodingAgent` (`dandy/application/agent/coding_agent.py`), which wraps `CodingBot`, a `PlanningBot` (`dandy/application/agent/bots/planning_bot.py`, THINKING config), and a persistent `MessageHistory`. `CodingAgent` (the CLI's child of the base `Agent`, see the agent bullet in [Tool calling](#tool-calling)) turns every typed message into an `agent.turn(...)`: its `_prepare_message` override runs the planning bot first (`run_planning`, default on — the planning bot starts from a fresh conversation on every turn, since the coding history already carries the context) and feeds the plan into the coding turn as an 'Implementation Plan' section of the user prompt. The base `turn` then compacts the persistent history, subtracting the real incoming prompt's token estimate (plan section included) from the 70%-of-`CONTEXT_SIZE` target (`AGENT_COMPACTION_TARGET_RATIO`; see [Environment & settings](#environment--settings-least-obvious-part) bullet 7), and raises `AgentRecoverableError` (printed by the CLI) if the history still exceeds the whole window afterwards, before calling `bot.llm.tools.prompt_to_intel(..., tools=AGENT_TOOLS, message_history=..., replace_message_history=True, max_tool_iterations=None)` so each turn keeps the prior conversation and the tool loop runs as many rounds as needed (no give-up cap, see [Tool calling](#tool-calling)). **Sessions persist automatically**: after every turn the REPL saves the active conversation through `SessionStore.for_project(session.project_base_path)` (`dandy/application/agent/session_store.py`, one JSON file per named session under `.dandy/agent/sessions/` — an agent-neutral location any agent over the project shares); the first turn auto-names the session `YYYY-MM-DD-<slug>` from the request text (collisions get `-2`/`-3`) and later turns update the same file. The `/` commands are `/new [name]` (fresh conversation, optionally pre-naming its session), `/sessions` (a table of name/updated/messages/tokens/model), `/resume <name>` (loads the session back into the agent via `agent.load_session`), `/delete <name>`, and `/quit`/`/exit` (stops the loop); anything else reports "Unknown command". The welcome banner always shows a session-status line (`session_banner_line` in `dandy/interfaces/cli/tui/printer.py`). Pressing **escape twice** in `Tui.get_user_input` (`dandy/interfaces/cli/tui/tui.py`) returns `None`, which breaks the loop. The old `ActionManager`/`/code`/`/explain`/`/help`/`/bot` action system and `dandy/cli/actions/` are gone; the agent lives in `dandy/application/agent/`, with bots in `dandy/application/agent/bots/` and tools in `dandy/application/agent/tools/`. **One-shot mode**: `dandy "<request>"` (entry point `dandy.interfaces.cli.main:main` in `pyproject.toml`) joins `sys.argv[1:]` and runs `process_user_input(user_input=..., save_session=False)` for a single stateless turn (no session file is created), then exits; `dandy --continue "<request>"` runs the one turn inside the most recently saved session (`agent.load_session`) and re-saves it under the same name, reporting `Saved session "<name>" (N messages).`; a bare `--continue` with no request prints usage. `dandy -h`/`--help` prints usage, `dandy -v`/`--version` prints the version, both before any settings load (`dandy/interfaces/cli/main.py`). The final answer (`result_intel.text` in `DandyCli.process_agent_input`) is printed through `Printer.output` (`dandy/interfaces/cli/tui/printer.py`), which renders it with `MarkdownRenderer` (`dandy/interfaces/cli/tui/markdown.py`) — a dependency-free markdown-to-terminal renderer (headings with dividers, inline bold/italic/code/links, fenced code blocks, lists, blockquotes, horizontal rules, and pipe tables) built only on blessed's `Terminal` styling and `wrap`. **`CLI_CONFIG` in settings** maps CLI task names to `LLM_CONFIGS` entries — `CodingBot.__post_init__` sets `self.llm_config = get_cli_llm_config('CODING')` (`dandy/shared/settings/load.py`), and the welcome banner shows that config's model; unknown/missing entries fall back to `'DEFAULT'`. A `DEBUG: bool = True` setting (see [Environment & settings](#environment--settings-least-obvious-part), `dandy/shared/settings/default_settings.py`) turns on verbose tracing: `DandyCli.__init__` reads it and, when true, passes a `verbose_callback` (prints each tool-round event from [Tool calling](#tool-calling) to stdout) into `CodingAgent.turn` → `prompt_to_intel`. When no `dandy_settings.py` exists, `CLI_CONFIG`/`LLM_CONFIGS` are resolved from a `dandy.json` fallback instead (see [JSON fallback](#environment--settings-least-obvious-part)). The toolset is `AGENT_TOOLS = CODE_EDITING_TOOLS + [search_files, run_command, git_status, git_diff]` (`dandy/application/agent/tools/`): the six file tools plus `SearchFilesTool` (grep-style, excludes `.git`/`.dandy`/`node_modules`/`.venv`/`__pycache__`, capped output), `RunCommandTool` (runs commands with no user confirmation), and `GitStatusTool`/`GitDiffTool` (all three set `timeout_seconds`/`use_shell`, override the `working_directory` property to `session.project_base_path`, and call `self.run_subprocess(command, ...)`; `use_shell=True` only on `RunCommandTool`); `ReadFileTool` and `ListDirectoryTool` also cap their output at 8000 characters with a truncation notice (every tool result is capped again by `ToolService` before it enters the conversation). Every path resolves against `session.project_base_path` and refuses paths that escape it; every `handle()` returns a string, never raises, so the model can self-correct. Covered hermetically in `tests/application/agent/` (tool unit tests, a mocked `request_to_response` `CodingAgent` multi-turn test asserting the second turn's request contains the first turn's user/assistant messages and that `clear()` resets the history, base-`Agent` turn/run tests plus a session save/load round-trip in `test_agent.py`, the hermetic `SessionStore` suite in `test_session_store.py`, and `DandyCli` loop tests for escape-exit, the session commands, turn auto-save, and one-shot `--continue` in `tests/interfaces/cli/`).
- **Compaction is fuzz-tested with hypothesis**: `tests/domain/message/test_compaction_fuzz.py` (strategies in `tests/domain/message/intelligence/compaction_fuzz_strategies.py`) draws a system-led, wire-well-formed conversation (plain exchanges + tool rounds whose results match their declaration's call ids, occasionally ending in an unfinished declaration) plus a 0–100k budget, and asserts six invariants of `compact_message_history`: the system slot survives, the result is an order-preserving subsequence of the input, tool rounds survive atomically in both directions (a surviving declaration keeps all of its results; a surviving result keeps a declaration before it with a matching call id), compaction is a fixed point, an under-budget history is untouched, and the result either fits the budget or is stuck at two messages or fewer (never empty). The tests are `unittest.TestCase` + `@given`, so they run under both pytest and CI's `unittest discover`; `hypothesis` lives in the `development` extra and its `.hypothesis/` example DB is gitignored.
- **`tests/nines/`** is a self-contained flakiness harness: `@nines_testing(n)` re-runs a function 10^n times to shake out nondeterminism; with no argument it defaults to the `TESTING_NINES` env var (`0` = run once). Not part of the library; `TESTING_NINES=1` is set by the `optional-testing` `workflow_dispatch` CI job (the nines-decorated test is `@live_llm_test`, so it needs a real key).
- **`tests/application/example_project/book/`** demonstrates full multi-bot orchestration (theme → title → characters → world → plot → chapters) with Intel flowing between bots (`create_book` in `book/workflow.py`). Best reference for "how to compose many bots". Its test (`test_book_generation`, `@live_llm_test`) takes ~110s against a live endpoint and is excluded from the hermetic path; it runs in the `optional-testing` CI job.
- Test directory quirks: `tests/infrastructure/recorder/`, `tests/nines/`.
- **Strict OpenAI-compatible endpoints (vLLM via litellm) reject conversations with more than one leading system message or system messages elsewhere** (400 `System message must be at the beginning.`). The connector only prepends its own system prompt when the merged `message_history` does not already lead with a system message, and diligence instructions merge into that leading system message instead of adding another (`BaseDiligence._prepend_system_instruction`). Preserve both behaviors when refactoring the request-building flow.
- **`MessageHistory` is falsy when empty** (it defines `__len__` and pydantic does not define `__bool__`), so the connector's history merge guard must be `if message_history is not None:` — never `if message_history:`. An empty history is a legitimate value when `replace_message_history=True`: it means "attach this (currently empty) history object so the conversation accumulates into it". `connector.py:_update_request_body_options` uses this to make multi-turn `CodingAgent.turn` calls persist into the caller's history.
- **Live models (e.g. `stratus.turbo`) often wrap the final JSON answer in markdown code fences**, which fails strict JSON validation; the connector's validation retry prompt and the `CodingBot` guidelines both now explicitly demand raw JSON (no fences, no extra text). On top of that, `LlmConnector._validate_fenced_json_response` (`dandy/infrastructure/llm/connector.py`) recovers when the model does it anyway: if the response contains exactly one fenced code block (` ``` ` or ` ~~~ `, language tag optional, a narration line before it is fine) and that block's body parses and validates against the target intel, it is used as the answer so the CLI renders text instead of a raw javascript block. When the fenced body does not validate (e.g. it is a legit code sample, or multiple fences exist), behavior is unchanged (raw-text fallback for `DefaultIntel`, retry loop otherwise). Keep those instructions when adjusting prompts.
- **`DefaultIntel` is prose-tolerant**: its whole purpose is "whatever text the model said", so `LlmConnector._request_to_intel` has a fallback — when the response is plain text (validation error type is exactly `json_invalid`) and the target Intel is `DefaultIntel`, it stores the raw text in `DefaultIntel.text` instead of failing. Wrong-key but valid JSON (e.g. `{"message": ...}`) still goes through the retry loop; only unparseable prose takes the fallback. This is what lets the agent REPL answer "how do I..." questions without crashing.
- Reset behavior is explicitly tested (`tests/application/bot/test_reset_chain.py`) — preserve the exact reset call graph if refactoring.

## Gotchas & non-obvious patterns

1. **Do not override `__getattribute__` in `Bot` subclasses** — the base already injects the recorder wrapper through it; overriding breaks recording (and typing). No `__getattribute__` in new bot code.
2. **The `Agent`/processor-pipeline module was removed in v2.0.0.** Compose multiple `Bot` instances (see `tests/application/example_project`) — there is no orchestrator class anymore.
3. **Bot subclasses must call `super().__post_init__()` first** when they define `__post_init__`; `ServiceCriticalError` guards rely on class attrs being set (`llm_config`, `role`, `task`, `intel_class` — see `LlmServiceMixin._required_attrs`).
4. **`Bot.process` requires a `prompt`**: it forwards `args[0]` as `prompt` or raises `ValueError`. Subclass `process()` to accept your own signature (see `tests/application/bot/intelligence/bots.py`) and call `self.llm.prompt_to_intel(...)`.
5. **Decision keys must be strings** — non-string keys raise `DecisionCriticalError` (a runtime check in `Decision.process()`).
6. **LLM configuration is OpenAI-compatible chat completions only** — `LlmConfig` forces path `v1/chat/completions`; the response parser reads `choices[0].message.content` (and `choices[0].message.tool_calls` when tools are used).
7. **Calling `request_body.json_schema`/`estimated_token_count` is only valid when `response_format` is set** — the tool path sets `response_format` to `None`; guards exist in the recorder and token estimator for that case, keep them.
8. There is a documented **"LLM freeze" trigger**: the prompt `'Please give me 22 coins and 17 gems.'` was observed to lock a model in indefinite inference and is deliberately commented out in `tests/application/bot/test_bot.py` — don't reintroduce it.
9. **Settings are a singleton imported once**; the CLI calls `settings.reload_from_os()` to pick up env changes. After editing `tests/dandy_settings.py` or env vars in a dev loop, restart the process.
10. Live-LLM tests skip locally (hermetic-by-default, see [Testing approach](#testing-approach)), so a missing key never fails `just test`; to run them, export a real `AI_API_KEY` first. They can be slow/flaky against real endpoints — `just test-failed` (`--lf`) is the targeted rerun.
11. `DEBUG=True` settings swap in `dandy.shared.debug`'s warning handler (prints stack traces for warnings) — useful when debugging LLM retry/validation flow.
12. Recorder output only persists to disk when `ALLOW_RECORDING_TO_FILE = True`; the `.dandy` artifact directory (and `recordings/`) is gitignored noise — don't commit it.
13. **`generate_cache_key` detects Dandy services structurally**: `convert_to_hashable_str` in `dandy/infrastructure/cache/key.py` hashes any object with a `recorder_event_id` attribute by class qualname (instead of dumping `__dict__`), so it does not need to import `Bot` — that would be an infrastructure → application edge the contracts forbid. Keep the check structural if you touch it.
14. **Packaging**: setuptools uses `[tool.setuptools.packages.find] include = ["dandy*"]` in `pyproject.toml` — auto-discovery would also pick up `archived_docs/` as a package and break the build. Keep the include filter if you add top-level directories.

## Documentation

- The live site is in `docs/`, configured by `mkdocs.yml` at the repo root (Material theme; plugins: search + mkdocstrings with the python handler; sphinx docstring style; a mermaid fence). Build output goes to `site/` (gitignored).
- Structure is DDD-first and written from scratch for v3.0.0 (the old tutorial-based site was not reused): `introduction/` (what + principles), `domain_model/` (ubiquitous language, bounded contexts, tactical patterns), `architecture/` (layering + enforced rules, service pattern, LLM call anatomy), `getting_started/`, `user_guide/` (one page per domain concept), `reference/` (one hand-written API page per layer, using `::: dandy....` mkdocstrings directives), `migration/v2_to_v3.md`, `changelog/v3.md`.
- **Design specs**: working feature design specs live at the repo root in `specs/` (not published; one per feature named by topic, `Draft` → `Implemented` lifecycle; conventions in `specs/README.md`). When a non-trivial feature starts, write the spec before the code.
- The `documentation` extra in `pyproject.toml` (`mkdocs`, `mkdocs-material`, `mkdocstrings[python]`) provides the build stack; `just docs` serves it and `just docs-tests` runs the strict build. The CI `documentation-testing` job mirrors that strict build.
- **mkdocstrings imports `dandy` at build time**, so the build needs the settings module: the justfile exports `PYTHONPATH` (with `.`) and `DANDY_SETTINGS_MODULE=tests.dandy_settings` globally, and CI sets the same job-level env. Running raw `mkdocs` from elsewhere needs those two set.
- Reference pages list members explicitly in each directive; when you add or rename a public symbol, update the matching `docs/reference/*.md` member list or the strict build's rendered API will drift. Docstrings are Sphinx-style and are what the reference renders — keep them accurate.
- `mkdocs build --strict` (or `just docs-tests`) is a CI gate — broken links, missing anchors, or unresolvable mkdocstrings symbols fail the build.
- The previous docs site (tutorials, changelog, roadmap, about, getting started) and its `mkdocs.yml` live in `archived_docs/` — read-only reference material: don't edit, extend, or sync it, and don't cite it as the live docs.
- When changing public API, update the docs in `docs/` (user guide page, the relevant reference member list, and `docs/changelog/v3.md`) to match.
