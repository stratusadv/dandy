# Changelog

## v3.0.0a4

### Added

- `HashMixin` (`dandy/shared/hashing.py`, exported from `dandy`): two-level
  state hashing for framework state classes. `shallow_hash()` is a cheap
  volume signal (long strings fingerprinted as length plus head and tail),
  `deep_hash()` is an exact state digest (canonical sorted-key form of the
  object's state, sha256 truncated to 32 hex chars), and `__hash__` is
  derived from the deep hash. Applied to `Message` / `MessageHistory`,
  `BaseIntel`, `LlmOptions`, `LlmRequestBody`, `BaseTool`, `BaseSkill`, and
  `LlmConfig` (whose hash deliberately excludes `api_key`).
- Guard framework (`dandy/domain/guard/`): `Guard` is a middleware-style
  watcher over a tool loop, `GuardChain` runs an ordered set of them over one
  loop, and `GuardEvent` / `GuardOutcome` carry the loop's events (round
  starts and executed tool calls) and the guards' verdicts. A guard that
  re-trips after it already issued a correction for the same signature counts
  an identical failure (the correction did not change the behavior), and a
  guard's failure stops the loop with `LlmRecoverableError` before the next
  HTTP call.
- `ContextPressureGuard` (`dandy/domain/guard/context_guard.py`): requests
  compaction once the conversation's estimated token count passes
  `COMPACTION_TRIGGER_RATIO` (0.80) of the resolved context window, and
  fails the loop when the pressure re-asserts after an issued compaction
  while the conversation still exceeds the whole window, so the provider
  never 400s an oversized request.

### Changed

- Tool-loop guarding moved from the `RepeatedCallGuard` class to the guard
  chain: `ToolService` now runs a `GuardChain` of a `RepeatGuard` and the
  `ContextPressureGuard` per loop, and compacts the conversation when the
  chain requests it (`ToolService._compact_history`, renamed from
  `_compact_history_before_next_round`).
- `RepeatGuard` (`dandy/domain/guard/repeat_guard.py`) counts executed calls
  by arguments alone, each against a full signature (tool name plus a digest
  of the exact canonical arguments) — from `REPEATED_CALL_WARNING_THRESHOLD` (3)
  on the tool result fed back to the model carries a steering note, and at
  `REPEATED_CALL_STOP_THRESHOLD` (10) identical calls the loop raises
  `LlmRecoverableError`. The old result counter is gone, which fixes the bug
  where a model that kept re-wording a command (different arguments,
  identical output) tripped the 10-call stop threshold: different arguments
  are different calls and never accumulate against each other, while
  re-typed calls with line-wrap, indent, or key-order drift still share one
  signature.
- Cache keys for `HashMixin` objects now derive from their `deep_hash()`
  digest instead of a structural attribute walk. The key format for those
  objects changed, so caches keyed on such objects (messages, Intel, LLM
  options or request bodies, tools, skills, configs) miss once after an
  upgrade until they refill.

### Removed

- `RepeatedCallGuard` and its two-counter design
  (`dandy/domain/tool/repeated_call.py`), replaced by the guard chain above.

## v3.0.0a3

The second alpha of the v3 line — a CLI-focused release: one command registry
now drives the REPL and the one-shot flags, the entry modules are split into
single-purpose files, and the REPL prompt gained inline command suggestions
with tab completion.

### Added

- Single-purpose CLI entry modules: the one-shot flag parser moved out of
  `main.py` into `dandy/interfaces/cli/one_shot.py` (`parse_one_shot` over
  `_scan_flags` + `_plan_for`, plus the `OneShotPlan` dataclass), and the `-h`
  usage text and the one-shot welcome banner moved into
  `dandy/interfaces/cli/usage.py` — `main.py` is now just the settings
  bootstrap and the REPL/one-shot dispatch.
- Unified CLI command registry with one-letter shorthands
  (`dandy/interfaces/cli/commands.py`): `CLI_COMMANDS` is now a frozen
  `CliCommand` entry per command (name, one-letter short, long and short
  one-shot flag, argument rule, description), and that single table drives the
  REPL dispatch, tab completion, the one-shot flag parser (`parse_one_shot` in
  `dandy/interfaces/cli/one_shot.py`), and the `-h` usage text, so the REPL and the
  one-shot flags cannot drift. Every REPL command gains a one-letter short —
  `/i`, `/n`, `/s`, `/r`, `/d`, `/q` — dispatch matches the full name or the
  short, tab completes a short to its full name, and `/sessions [name]`
  (i.e. `/s [name]`) doubles as resume when a name is given. One-shot mode
  gains a long and a short flag for every command: `dandy -s` (or
  `--sessions`) lists the saved sessions and exits 0, `dandy -s <name>` (or
  `-r <name>`) loads that session and opens the interactive REPL on it,
  `dandy -s <name> "<request>"` runs the one turn inside it and re-saves it
  (the exit code follows the turn), and `--new`/`-n`, `--delete`/`-d`,
  `--init`/`-i` cover the rest. The parser treats a token as a flag only when
  it exactly matches a known long/short flag or `--continue`, so free-form
  requests may safely contain dashes; `resume` and `delete` consume the next
  token as the name (required), and `sessions` and `new` consume it only when
  it is not itself a known flag; two action flags, `--init` with a request, or
  a bare `--continue` print usage. Slash-form one-shots (`dandy /sessions`,
  `dandy /s <name>`) keep working: anything not consumed as a flag joins into
  the request and routes through `process_user_input`.
- Inline command suggestions and tab completion in the REPL prompt
  (`dandy/interfaces/cli/tui/tui.py`): when the first character typed is `/`,
  a grey suggestion shows **inline on the input line itself**, after the typed
  text (`⦿ /s  /sessions`, bash-history-hint style), listing every command
  matching the typed prefix by full name or one-letter short, re-evaluated on
  every keystroke, backspace, and tab; tab completes the command word to the
  unique match or the longest common prefix of the matches. The suggestion is
  cleared on enter and on exit so it never leaks into the next output, hidden
  once a space is typed or prefix + buffer + suggestion would exceed the
  terminal width, and question prompts never suggest. Every keystroke runs one
  idempotent full-line re-render from column 0 (a single `CR` + clear-EOL +
  write), which self-heals dropped bytes and makes cursor-column bugs
  impossible; when the input wraps to multiple visual lines, that same single
  write first clears the previous render's rows (the row the cursor sits on,
  then a `CSI A` + `CR` + clear-EOL climb back to the block's first row), so
  a wrapped block is always cleared and rewritten top-down and backspacing
  never leaks a duplicate of the row above. Screen-level regression tests
  (`tests/interfaces/cli/test_tui.py::TestTuiCommandCompletionScreen` and
  `::TestTuiMultiLineInput`) run on
  a minimal VT emulator (`tests/interfaces/cli/intelligence/screen.py`) that
  can simulate wide-rendering characters.
- Per-instance, mid-conversation LLM config changes: `bot.llm.set_config(name, **overrides)`
  (`dandy/application/llm/service.py`) swaps the bot's resolved `LlmConfig` to
  another settings `LLM_CONFIGS` entry and/or individual fields — the identity
  fields `model`, `host`, `port`, `api_key`, `context_size`,
  `prompt_retry_count`, plus any `LlmOptions` field — without touching the
  in-flight conversation (the next request goes to the new endpoint and model
  with the same history), and `bot.llm.config` is now settable with a fully
  prepared `LlmConfig` (exported from the `dandy` root). Unknown override
  names, wrong types, and out-of-range option values raise
  `LlmCriticalError`; the bot's `llm_config` name stays in sync with the active
  entry. `LlmConfig` gains first-class `host` / `port` / `api_key` properties
  (the host setter keeps `Url.parsed_url` fresh, the api_key setter
  regenerates the Authorization header), and `LlmConnector` now syncs the
  config's model into the request body on every call, so every config field
  takes effect on the next request. Per-instance changes survive
  `bot.reset()`, which re-applies the options of the instance's *current*
  config. `Decision` reads the live config instead of its construction-time
  snapshot, and `Agent` re-resolves its `CONTEXT_SIZE` window at the start of
  every turn (and gains a thin `agent.llm` property reaching the bot's LLM
  service), so tool loops, compaction, and decisions all track a mid-flight
  switch.

### Changed

- Version set to 3.0.0a3 (`dandy.shared.constants.__VERSION__`).

## v3.0.0a2

The first alpha of the v3 line. It combines the
breaking, structure-focused reorganization — the package was physically reorganized
into a four-layer, domain-driven design with an enforced dependency model — with the
first round of new capabilities (the `Agent` base class, skills, session
persistence, and the agentic CLI loop). Internal import paths changed everywhere;
see the [migration guide](../migration/v2_to_v3.md) for the old-to-new map.

### Added

- `tool_call_callback` on `ToolService.prompt_to_intel`, `Agent.turn`, and
  `Agent.run` (`dandy/application/tool/service.py`): fired once per executed tool
  call with the tool name and its validated keyword arguments (after the
  `handle()` / `tool_function` dispatch, so invalid-argument calls never fire it).
  The CLI uses it to track the paths its file tools touched and the action —
  `write_file` / `create_directory` (added), `edit_file` (modified),
  `delete_file` (removed) — and prints file-change sections below the
  model's final answer: one `Added Files`, `Modified Files`, or `Removed
  Files` section per non-empty action, each a bold blue heading over a thin
  blue border with one `• path` bullet per file colored by action
  (green/blue/red), each a clickable OSC 8 `file://` link; when a file was
  touched by more than one action the last one wins, and paths keep
  first-seen order. Nothing prints when no such tool ran.
- Clickable file paths in CLI story beats: a tool beat's description wraps every
  path-like token in a raw OSC 8 `file://` hyperlink (relative paths resolve
  against the project root) so clicking a file in the running story opens it
  with the OS default handler. The sequence is emitted directly because
  blessed's `hyperlink` terminfo capability is unavailable.
- `BaseTool.can_mutate_state` (`dandy/domain/tool/tool.py`, default `False`): a
  class attribute marking tools that can change state. `StoryBeat` carries the
  flag on tool action beats, and the CLI story renders such labels in bold
  orange instead of grey in both the animating and settled frames. The
  file-mutating agent tools (`write_file`, `edit_file`, `delete_file`,
  `create_directory`) and `run_command` set it `True`.
- `Agent` (`dandy/application/agent/agent.py`), exported from the `dandy` root:
  the stateful, loop-ready base class for agentic use cases. A `turn` is one
  exchange over a persistent `MessageHistory` (one tool loop, many rounds, with
  the same 70%-of-`CONTEXT_SIZE` compaction as the CLI agent); `run(request)`
  drives turns until the turn result's `done` field (or an `is_done` callback)
  signals completion, bounded by an optional `max_turns` (default unbounded,
  giving up with `AgentRecoverableError`). Turn results default to
  `AgentTurnIntel` (`text` + `done`); `run` without a `done` field and no
  `is_done` fails fast with `AgentCriticalError`. The compaction constants
  (`DEFAULT_CONTEXT_WINDOW`, `COMPACTION_TARGET_RATIO`,
  `COMPACTION_TRIGGER_RATIO`) live in `dandy/domain/message/compaction.py` and
  are shared by the agent and the tool loop.
- Glossary terms: `Agent`, `turn`, `run` (the run > turn > tool-round ladder).
- `BaseSkill` (`dandy/domain/skill/skill.py`), exported from the `dandy` root: a named
  bundle of a prompt and typed methods. Active skills put their prompt in the system
  message and their methods in the tool list from the first request; passive skills
  contribute name + description until the model calls the built-in `activate_skill`
  tool, which delivers the prompt as a tool result and adds the methods as
  `{skill}_{method}` tools (activation is one-way per conversation). Register on a
  `Bot` class attribute (`skills=[...]`) or as an `Agent` constructor argument.
  `SkillService` (`dandy/application/skill/service.py`) owns the registry on
  `bot.llm.skills`; `LlmService` gains `append_system_prompt` for post-init skill
  registration.
- Glossary term: `Skill` (active / passive / activation).
- `Dandy` namespace (`dandy/__init__.py`): `from dandy import Dandy` reaches the whole
  public API as attributes (`Dandy.Bot` *is* `dandy.Bot` — a pure re-export, for
  one-import usage and IDE discovery). The public API also gains four documented
  names: `LlmOptions`, `DefaultIntel`, `MessageHistory`, `Decision`.
- Property-based compaction tests: a hypothesis battery
  (`tests/domain/message/test_compaction_fuzz.py`, strategies in
  `tests/domain/message/intelligence/compaction_fuzz_strategies.py`) draws
  system-led, wire-well-formed conversations and asserts six invariants of
  `compact_message_history` (system slot survival, order-preserving
  subsequence, atomic tool rounds, fixed point, under-budget no-op,
  fits-or-maximally-compacted: when still over budget, no `user`/`assistant`
  message remains between the protected opening exchange and the newest). `hypothesis` joins the `development`
  extra; the tests run under both pytest and `unittest discover`.
- Agent session persistence: `Agent.save_session()` / `Agent.load_session()`
  snapshot and restore the conversation (a fresh `MessageHistory`, the last
  request, and a bot reset), so a conversation can outlive the process.
  `AgentSession` (`dandy/application/agent/intel.py`) carries the message
  history plus metadata (last request, model and config names, estimated token
  count); `SessionRecord` pairs it with a name and created/updated timestamps.
  `SessionStore` (`dandy/application/agent/session_store.py`) reads, writes,
  lists, deletes, and auto-names one JSON file per named session under a
  directory; `SessionStore.for_project(path)` targets
  `<path>/.dandy/agent/sessions/` (agent-neutral, so any agent over the same
  project shares the location), and `new_name(text)` derives a fresh
  non-colliding `YYYY-MM-DD-HH-MM-<slug>` name from request text.
- CLI conversations are saved automatically: every turn saves regardless of
  outcome (success, stop, or error) through one shared turn path used by the
  REPL and both one-shot forms, so plain one-shot (`dandy "<request>"`) now
  saves a new auto-named session instead of running stateless; an incomplete
  trailing tool round is dropped from the snapshot before it is written
  (`drop_incomplete_tool_round` in `Agent.save_session`) so a crash mid-round
  leaves a session that resumes cleanly. The welcome banner always shows a
  session-status line, and the commands are `/new [name]` (fresh conversation,
  optionally pre-named), `/sessions` (a table of saved sessions: name,
  updated, messages, tokens, model), `/resume <name>` (load one back into the
  agent), and `/delete <name>`. One-shot gains `dandy --continue "<request>"`,
  which runs one request inside the most recently saved session, reports
  which session it used, and re-saves it under the same name through that
  same shared path.
- Repeated tool-call guard in `ToolService` (`dandy/application/tool/service.py`):
  two per-loop counters, neither consecutive-only. The signature counter
  accumulates every call whose (name, canonical arguments, result) triple
  repeats — arguments are canonicalized (`_canonical_arguments`: whitespace runs
  folded in every string value, sorted-key compact JSON of the validated kwargs)
  so a model that re-types a call with line-wrap, indent, or key-order drift
  still accumulates toward one signature. The result counter accumulates
  (name, result) pairs across any argument wording, so a reworded call that
  keeps producing the same output is caught too. A model that oscillates between
  a few near-identical calls accumulates; a changed result never accumulates
  toward either counter, so legitimately time-varying commands never trip them.
  The tool result fed back to the model carries a steering note from
  `REPEATED_CALL_WARNING_THRESHOLD` (3) occurrences on, telling it to change
  approach or give its final answer, and the loop raises `LlmRecoverableError`
  at `REPEATED_CALL_STOP_THRESHOLD` (10); a degenerate model now costs a bounded
  number of rounds instead of burning the whole (possibly unbounded)
  tool-iteration cap.
- AGENTS.md project instructions for the CLI: when `<project>/AGENTS.md` exists,
  its content is folded into the `CodingBot` guidelines as a
  'Project Instructions' section, so it is part of the system message for every
  turn (and for one-shot mode); the welcome banner shows a status line for it.
  The `/init` REPL command and the `dandy --init` one-shot flag run the init
  pass: a dedicated `InitBot` (`dandy/application/agent/cli/intelligence/bots/init_bot.py`)
  explores the project with the normal agent tools, inlines the existing
  AGENTS.md into its prompt when one exists (kept claims verified, stale ones
  corrected), and writes the refreshed file to the project root; on success
  `CliAgent.reload_agents_md` re-reads the file and syncs the running
  conversation's system message (via the new `LlmService.rebuild_system_prompt`)
  so the new instructions apply to the next turn without `/new`. `dandy --init`
  exits with code 1 when no file was written.
- `QuestionTool` and the `question` agent tool
  (`dandy/application/agent/intelligence/tools/question/question_tool.py`): the model can ask
  the user a question mid-turn and wait for the answer. The tool takes a
  required `question` plus an optional `choices` string array; the CLI renders
  the choices numbered and accepts either a number or free text, and the
  answer is fed back to the model as the tool result. `CliAgent` carries the
  tool as a configured instance (an injected `ask_user` callable; without one
  the tool answers "no user available — make a reasonable decision and
  proceed", so it is safe headless), while the init pass keeps the plain
  `AGENT_TOOLS` without it. The CLI wires `ask_user` to a shared
  `QuestionGate` (`dandy/shared/interaction.py`, a `question_gate` singleton
  mirroring the `stop_signal` pattern): the agent's worker thread parks the
  question and blocks, the terminal-owning render loop of
  `Printer.run_timed_task` (new `question_gate` / `question_handler`
  parameters) prompts on the main thread and delivers the answer. Double
  escape while a question is on screen stops the run exactly like anywhere
  else (the gate sets the stop signal and hands the worker a stop sentinel).
- `save_session_json()` / `load_session_json(session_json)` on `Agent`
  (`dandy/application/agent/agent.py`): the `save_session` / `load_session`
  snapshot as a JSON string, for stores the app owns itself (a database
  column, a queue payload, a cache). This is the worker pattern: one agent
  instance, one `turn` per received message — load the session JSON for the
  message's conversation (or start fresh), turn, write the JSON back — and
  the same instance serves any number of conversations because
  `load_session_json` replaces the history and resets the bot. A string that
  does not validate as an `AgentSession` raises `AgentRecoverableError`
  without touching the live conversation.
- Clickable file links in the final answer: `MarkdownRenderer`
  (`dandy/interfaces/cli/tui/markdown.py`) now linkifies file paths in the prose
  it renders (paragraphs, headings, list items, table cells, blockquotes, inline
  code spans, and markdown link labels) with the same raw OSC 8 `file://` links
  the story beats and the file-change sections use (relative paths resolve against
  the project root), so clicking one opens the file with the OS default
  handler. The `linkify_file_paths` helper moved to
  `dandy/interfaces/cli/tui/text.py`, where both the printer and the renderer
  import it; fenced code blocks are never linkified, URLs are untouched, and
  blessed's `term.length`/`term.wrap` handle the escape sequences so wrapping
  and table layout are unchanged.
- Architecture enforcement with import-linter: six contracts in `pyproject.toml`,
  a `just lint-imports` recipe, and an "Architecture Tests" step in CI. Cross-layer
  imports outside the documented seams now fail the build.
- A documentation site rebuilt from the ground up around the domain model:
  ubiquitous language, bounded contexts, tactical patterns, architecture,
  getting started, a concept-by-concept user guide, and a per-layer API reference
  (mkdocs + Material + mkdocstrings).

### Changed

- The CLI's agent question prompt displays like a story action: an empty line,
  the tool's action label (`Asking`) and the `↳` arrow in plain purple, and the
  question text in plain black to the right of the arrow on the same line (the
  old `Question: ` prefix is removed), and both dividers around the prompt —
  under the choices and after the answer — are plain purple instead of bold
  purple and bold grey (`Printer.divider` is removed with its last caller).
  `QuestionTool` sets the new `BaseTool.emits_story_beat = False` so the tool
  loop emits no story beat for it and the question appears exactly once, in
  the prompt (its `action_output` override goes with the beat).
- CLI story tool beats are prefixed by a fixed `↳` arrow colored like the
  beat's label (bold skyblue for read-only tools, bold orange for
  `can_mutate_state` tools) instead of a per-tool character.
- The CLI story renders consecutive tool beats with the same label as a simple
  list under a heading instead of repeating the label on every line: the label
  prints once as a heading line (bold skyblue, bold orange when `can_mutate_state`
  is set) when it appears and again whenever the label changes or a non-tool
  line (a thought or a system notice) has printed since the last one, so a
  repeated label after a thought is no longer a bare bulleted detail line;
  each beat's description prints on its own line below the heading prefixed by
  its `↳` arrow. Bullets exist only on those tool output lines; non-tool
  beats (narration, system notices, the opening thinking phrase) print with no
  prefix at all.
- `LlmOptions` (`dandy/domain/request/options.py`) now mirrors the full OpenAI Chat
  Completions request parameters instead of a fixed set of five. The declared fields are
  `frequency_penalty`, `logit_bias`, `logprobs`, `max_completion_tokens`, `max_tokens`,
  `n`, `presence_penalty`, `reasoning_effort`, `response_format`, `seed`,
  `service_tier`, `stop`, `temperature`, `top_logprobs`, `top_p`, with `extra='allow'`
  keeping any other option the endpoint understands. Non-None values are still
  range-checked (temperature 0–2, penalties –2 to 2, `top_p` 0–1, and positive minimums
  for `max_completion_tokens` / `max_tokens` / `n`).
- `max_completion_tokens` is no longer derived from `CONTEXT_SIZE` by
  `LlmConfig.generate_request_body` — it is now a normal option you set in a config's
  `OPTIONS` (or on `bot.llm.options`). When omitted, the request does not send it. The
  previous `LLM_OUTPUT_TOKEN_RATIO` constant (0.20) is removed.
- `prompt_retry_count` is no longer a field on `LlmOptions`. It is read by `LlmConfig`
  from a per-config `PROMPT_RETRY_COUNT` setting key (default `2`) and used for the
  validation-retry budget, so it no longer leaks into the request body.
- `CliAgent` now extends the base `Agent` instead of reimplementing the
  loop: the compaction and context-window logic are inherited (the compaction
  target subtracts the real incoming prompt's token estimate), and the per-turn
  flow is compaction, then the tool loop. This makes the fit check
  (`AgentRecoverableError` when the history still exceeds the window after
  compaction) and session save/load available to the CLI agent for free.
- The base `Agent.turn` pre-flight fit check now runs for every agent (not
  just the CLI agent): when the history plus the incoming message still
  exceeds the whole context window after compaction, `turn` raises
  `AgentRecoverableError` before anything is sent.
- One-shot CLI exit codes: `dandy "<request>"` and `dandy --continue
  "<request>"` now exit with code 1 when the agent's turn fails (`main()`
  returns the exit code, wired through `DandyCli.last_turn_succeeded` and
  `continue_latest_session`'s bool return), so scripts can detect a failed
  turn; previously a failed one-shot still exited 0. The interactive REPL is
  unchanged: a failed turn prints the error and the loop continues.
- The token estimator is calibrated against real API prompt-token counts
  (`dandy/domain/tokens/estimate.py`): all character content runs through
  `TOKEN_COUNT_CALIBRATION_SCALE` (1.055), and
  `MessageHistory.estimated_token_count` adds `TOKEN_COUNT_REQUEST_OVERHEAD`
  (2633) per request — the framing the per-message sum never sees, chiefly the
  tool function definitions sent alongside the messages. Both constants were
  fitted against provider-reported `prompt_tokens` (251 requests across two
  agentic coding sessions) and are accurate to a handful of tokens
  in the 16k–40k size range where compaction decides. `compact_message_history`
  and the 70%/80% compaction budgets now work in these calibrated units, so the
  reserved headroom exists in the provider's count instead of being eaten by
  the old 1.1x–1.5x under-count, which left almost no margin at the compaction
  point.
- Tool story beats are structured: `BaseTool.action_sentence` is split into an
  `action_label` class attribute (next to `name` / `description`) and an
  `action_output(**validated_args)` override that returns the per-call detail
  (file paths, commands, ...). `ToolService.prompt_to_intel` (and
  `Agent.turn` / `run`) now pass `StoryBeat` objects
  (`dandy/domain/tool/beat.py`, exported from `dandy.domain.tool`) through
  `progress_callback` (typed `Callable[[StoryBeat], None]`) instead of plain
  strings: tool beats carry `label` (the `action_label`, or the title-cased tool
  name) plus `description` (the `action_output`), while narration and
  compaction beats are description-only (narration beats are marked
  `kind='narration'`, compaction beats `kind='compaction'`). The CLI story renders
  the label in bold grey, the description in plain black, and the model's
  narration in bold blue in both the animating and settled frames, so each part
  can be styled independently.
- CLI story output is flush left: the task header, completion, and error lines
  print as plain flush-left `Printer.event` lines. `Printer.indented_event` is
  renamed to `Printer.event`, and the unused `start_task` / `end_task` /
  `blank_line` helpers are removed.
- The `edit_file` tool's success result now identifies the edit:
  `Applied N replacement(s) to "path" (line N: "snippet")`, using a `lines N-M`
  range for multi-line matches, where the snippet is the first non-empty line
  of `old_string` capped at 40 characters. Previously every successful edit of
  a file returned the same generic string, so parallel edits to one file
  accumulated toward the repeated-call guard's result counter and drew
  false-positive steering notes; distinct edits now yield distinct results,
  while a genuinely repeated identical call (e.g. an `old_string == new_string`
  no-op on an unchanged file) still yields the identical result, so the guard
  keeps catching true edit loops.
- The CLI story's animating line is now a thinking phrase on its own line
  below the newest beat: a bold blue random phrase drawn once and held for
  three seconds (the phrase line carries no animated dots — the cycling
  dots rendered as garbage on some terminals), so the newest beat of a running
  task is clearly marked as waiting for the next step. The live region (the
  beat line plus the phrase line, plus a heading line or leading blank line
  when one is present) is redrawn in place every tick so it never appends to
  the scrollback: the animating frame folds a multi-line description onto the
  single line above the phrase line, and settling prints the beat in full
  while clearing every line it overwrites, so no tail of the longer animating
  frame survives. The leftover phrase line is reused as the first line of the
  next region, so beats within a group settle with no blank line between them,
  while each heading and narration keeps its blank line before it. When a
  question prompt pauses the animation, the newest beat settles first and the
  prompt lands at column zero on a fresh line. The heading label is bold
  skyblue (bold orange when the beat can mutate state) instead of bold grey,
  and `Printer.run_timed_task` no longer takes an `action_name` parameter —
  the task header is just the task text in bold orange.
- Compaction notices in the CLI story are their own `kind='compaction'` beat
  instead of a plain `kind='system'` line: they now read "Compacting my
  thoughts into a more manageable size" (the old
  "Compacting conversation history (N tokens)..." text is gone) and render in
  bold purple on their own line after a blank line, in both the animating and
  settled frames.
- Tests reorganized to mirror the new layout (`tests/domain/`,
  `tests/application/`, `tests/infrastructure/`, `tests/interfaces/`,
  `tests/shared/`).
- Version set to 3.0.0a2 (`dandy.shared.constants.__VERSION__`).

### Fixed

- Tool output is capped at 8000 characters before it enters the conversation,
  from one shared helper: `truncate_output` and `OUTPUT_CHARACTER_LIMIT`
  (`dandy/shared/utils.py`) cut at the limit, back up to the last newline when
  one exists, and append a `... (truncated)` marker. `ToolService` applies it
  to any result returned by a tool's `handle()` or an external handler, and the
  built-in `read_file`, `list_directory`, and `search_files` tools apply it to
  their own output (the subprocess helper uses it too). A large file read could
  previously overflow the context window, or be silently dropped whole by
  compaction before the model ever saw it.
- When the conversation still exceeds the context window after compaction drops
  everything droppable, the CLI agent raises an `AgentRecoverableError` with an
  actionable message (the CLI shows it) instead of sending a request the provider
  will reject with an opaque 400.
- `compact_message_history`'s docstring no longer claims the newest message is
  always kept: when the newest message is a `tool` result, its whole round (the
  assistant tool-call declaration plus its results) is dropped, because a tool
  result without its declaration is invalid on the wire. Behavior was already
  wire-correct; the docs now say so.
- Compaction no longer drops the original request: the opening exchange (the
  first `user` message; when it is a tool round, its assistant declaration and
  tool results as well) is protected, so a long session that compacts repeatedly
  can no longer lose sight of the task it was asked to do and wander.
- `HttpConnector.request_to_response` now retries connection errors (resets,
  SSL failures, proxy errors, DNS hiccups) alongside timeouts instead of
  surfacing them immediately as an unhandled exception, and other request
  errors (bad URL, too many redirects) still fail fast without burning the
  retry budget. When every attempt fails without a response, the
  `HttpConnectorRecoverableError` now names the last network error (for
  example `ReadTimeout: HTTPSConnectionPool(...): Read timed out.`) instead of
  only the generic "Unknown Reasons or Connection Timeouts" sentinel.

### Removed (breaking)

- The per-turn planning pass: `CliAgent` no longer runs a `PlanningBot`
  planning conversation before each turn — there is no `run_planning` flag and
  no 'Implementation Plan' section folded into the turn prompt. Every turn goes
  straight to the coding bot, so a turn is a single model conversation and a
  planning failure can no longer take a turn down with it. `PlanningBot` and
  `planning_guidelines_prompt` are removed with it.
- `CliAgent.chat` — replaced by the inherited `Agent.turn` (call
  `agent.turn(message)` instead). Code that called `CliAgent().chat(...)`
  must move to `.turn(...)`.
- The REPL's `/clear` command — `/new` supersedes it (it does the same reset
  and additionally unbinds the active session name, or pre-names a new one).
- `DandyCliSession.load` / `save` / `is_loaded` / `session_file_path` and the
  `.dandy/cli/session.json` file they wrote: that file only ever recorded the
  project path and a loaded flag, never a conversation, so it is retired. Real
  conversation persistence lives in `.dandy/agent/sessions/` (see Added above).
- `BaseTool.action_sentence` — replaced by the `action_label` class attribute
  plus the `action_output(**validated_args)` method (see Changed above), and
  `progress_callback` no longer receives plain strings — it receives
  `StoryBeat`s, so any custom callback must read `.label` / `.description`.
  The service no longer strips a trailing period from action beats; an
  `action_output` result is shown verbatim next to the label.
- `dandy/core/` (split into the shared kernel and the infrastructure layer).
- The one-line re-export shims in `dandy/infrastructure/file/`
  (`utils.py`, `exceptions.py`, and the `audio/` / `image/` subpackages); the real
  implementations live in `dandy/shared/files.py` and `dandy/shared/media.py`.
- The old tutorial-based docs tree and the heavyweight `documentation` extra,
  replaced by a slim one (`mkdocs`, `mkdocs-material`, `mkdocstrings[python]`).
